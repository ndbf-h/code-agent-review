# v1.1 之后的代码优化方案

> 审查基线：`f8d00fe...b7aff0c`（生产级打磨 REQ-01 到 REQ-17，含 v1.1.0 / v1.1.1），149 个文件，+12781 / −3783。
> 审查方式：代码审查分两条线并行——规范（对照 `CONTRIBUTING.md` 与常见代码坏味道）和需求（对照 `docs/superpowers/specs/2026-09-14-production-readiness-prd.md` 逐项核对），关键结论已对照源码二次确认。本轮只读，未执行 lint / test / build。
> 本文件只给方案，不含代码改动。每个批次落地时按 `CONTRIBUTING.md` 开短分支、跑提交前验证清单，并回到本文件的「进度台账」登记。

## 一、审查结论摘要

整体判断：17 项需求的主体都已经落地，测试覆盖也比较扎实（server 31 个测试文件 / 235 个用例）。问题集中在两类：一是新功能**接缝处的行为缺陷**（Webhook 链路、预算治理、审查配置的生效范围）；二是**单一真源被破坏**（配置、共享类型）。不需要大改架构，按风险从高到低分 6 个批次修复即可。

| 级别 | 数量 | 说明 |
| --- | --- | --- |
| P0 缺陷（行为错误 / 安全） | 5 | 必须先修，影响正确性或数据安全 |
| P1 设计偏差（实现与规格不符） | 5 | 功能“看起来能用”，但没有达到 PRD 的约束 |
| P2 可维护性 | 6 | 代码坏味道与结构问题，不影响当前行为 |
| P3 流程与文档 | 4 | 台账、注释、提交与分支规范 |

## 二、问题清单

### P0 缺陷

#### P0-1 Webhook 建任务不创建 agents 记录，审查对话历史会静默丢失

- 位置：`server/src/integrations/github/webhook.ts:115-122`（`defaultCreateReviewTask`）
- 现象：`POST /api/tasks` 的流程是 `createTask → createAgentsForTask → appendTaskEvent(task_queued) → publishTask`（`routes/tasks.ts:118-124`），Webhook 路径只做了 `createTask` 和 `publishTask`。
- 后果：
  - `messages.agent_id` 外键引用 `agents(id)`（`db/migrations/001_initial_schema.ts:32`）。orchestrator 持久化对话时（`orchestrator.ts:226`、`:561`）插入会因外键失败，失败被 `try/catch` 吞掉只打日志，Webhook 任务的审查对话历史全部丢失；`tool_calls` 同理。
  - 任务详情页的 agent 列表为空；事件流缺少 `task_queued`，前端排队态不一致。
- 根因：「创建并入队一个审查任务」的流程在两处各写了一份（Shotgun Surgery），Webhook 那份漏了步骤。

#### P0-2 收尾时被取消的任务仍会回写 PR 评论

- 位置：`server/src/queue/consumer.ts:305`（正常路径）、`:219`（缓存命中路径）
- 现象：`commentReportToPullRequest` 在 `completeTask`（`:315`）之前执行。任务在收尾瞬间被取消时，`completeTask` 抢不到状态并按取消结算，但评论已经发到 PR 上。缓存路径同样先评论、后 `updateTaskStatus`。
- 附带问题：外部 HTTP 调用耗时被计入任务耗时（`durationMs`），评论失败虽被吞掉，但网络慢时会拖长任务的“运行中”窗口。

#### P0-3 Webhook 同步拉取文件，超时重投会产生重复任务和重复评论

- 位置：`webhook.ts:172-183`
- 现象：在返回响应之前，逐个串行调用 `getFileContent` 拉取 PR 的全部文件。GitHub Webhook 的超时约 10 秒，超时后会重投；服务端没有按 `repo + prNumber + headSha` 去重，也没有记录 `X-GitHub-Delivery`。
- 后果：大 PR 或 GitHub API 慢时，同一个提交会被审查多次、评论多次，LLM 成本成倍增加。

#### P0-4 脱敏只覆盖了 `finalReport.issues`，`agentResults` 中的密钥原文仍会外泄

- 位置：`orchestrator.ts:768-772`
- 现象：REQ-10 的 `redactSecrets` 只作用在 `finalReport.issues` 上，`agentResults[*].issues` 原样保留。
- 外泄出口：
  - Markdown 导出与 PR 评论的「各维度发现」章节直接渲染 `agentResults`（`export/markdown.ts:79-90`）。若代码里有密钥并被某个维度引用到 message 或 suggestion，就会被**公开发到 GitHub PR 上**。
  - 前端按维度查看（`client/src/views/ReportView.vue:140`）。
  - 语义缓存中存储的报告。
- 与 CHANGELOG 中「报告输出与规则引擎命中片段不再包含密钥原文」的承诺不一致。

#### P0-5 LLM 配置有两个来源，默认 baseUrl 不一致

- 位置：`server/src/agent/llm-client.ts:20`、`:56-68`；对照 `server/src/config.ts:98-101`、`:213-220`
- 现象：`config.ts` 已用 zod 校验 LLM 配置，并按 provider 选择默认 baseUrl；但 `llm-client.ts` 仍直接读 `process.env`，默认值写死为 `https://api.deepseek.com`，并发数和重试次数也各自 `parseInt`。
- 后果：`LLM_PROVIDER=anthropic` 且未填 `LLM_BASE_URL` 时，config 认为地址是 Anthropic，实际请求却发往 DeepSeek；`LLM_MAX_CONCURRENCY=abc` 这类非法值能通过 llm-client（得到 `NaN`），绕过了 config 的校验。REQ-03「配置单一真源」的目标在最关键的模块上没有达成。

### P1 设计偏差

#### P1-1 token 预算对并行 reviewer 基本不起作用（REQ-11）

- 位置：`orchestrator.ts:609-639`、`agent/budget.ts`
- 现象：四个 reviewer 由 `Promise.allSettled` 同时启动，`budget.isExceeded()` 只在每个 reviewer 启动时检查一次。此时只计入了编排阶段的 token，reviewer 运行中再怎么超支也不会触发降级，`react-loop` 的迭代中也没有预算检查。
- 结论：预算只能挡住「编排阶段就已超支」这种极端情况，起不到控制单任务成本的作用。

#### P1-2 审查配置的过滤与截断只作用于顶层 issues（REQ-14）

- 位置：`orchestrator.ts:774`
- 现象：`applyReviewConfig` 只处理 `finalReport.issues`。`agentResults` 不过滤；评分仍按全部问题计算；`consumer.ts:298-302` 用 `agentResults` 算平均分。
- 后果：用户设置 `severityThreshold=critical` 后，按维度查看、Markdown/SARIF 导出、评分仍包含被过滤掉的问题，配置看上去「没生效」。

#### P1-3 Webhook 的代码收集策略过于粗糙（REQ-15）

- 位置：`webhook.ts:84-113`、`:133`、`:183`
- 问题：
  1. 遇到第一个超出总量上限的文件就 `break`，后面较小的文件全部丢弃；应改为 `continue`，并在报告中注明被跳过的文件。
  2. 没有单文件上限（PRD 要求「单文件与总量上限」）。
  3. `express.raw` 的 `limit` 写死为 `5mb`，与 `MAX_BODY_SIZE` 不联动。
  4. 语言写死为 `'mixed'`，规则引擎按语言匹配规则，多数规则不会命中。应按扩展名推断主语言，或按文件分别标注。

#### P1-4 前端仍手写一份共享类型（REQ-12 / CONTRIBUTING §九）

- 位置：`client/src/types/index.ts:1-51`
- 现象：PRD 要求「与 shared/types.ts 重复的类型改为从 shared 重新导出」，实际不但没改，还新增了 `ReviewConfig`、`ReportSecurity`、`ReportGovernance` 三个副本。两边已经分叉：`InjectionFinding`（shared）对 `ReportInjectionFinding`（client）；client 缺少 `TaskSource`；`agentResults` 的类型也不同。
- 后果：服务端字段变化时前端不会收到类型报错，回归只能靠人工发现。

#### P1-5 其余配置直读点没有收口，也没有登记待办（REQ-03）

- 位置：`tools/rag/providers.ts:20-35`、`observability/tracing.ts:125-133`、`agent/role-router.ts:76`、`mcp/client.ts:91`、`tools/rag/index.ts:31`、`logger.ts:36-45`
- 现象：PRD 允许这些点分批迁移，但要求「列入 CHANGELOG 待办」，CHANGELOG 中没有对应条目。`logger.ts` 的 `envDefaults()` 还重复实现了 `config.ts:232-233` 的日志级别与格式默认值逻辑。

## 三、实施方案

原则：

- 每个批次一个短分支，从最新 `develop` 拉出，完成后合回 `develop`；全部完成后统一合入 `master` 并打 `v1.2.0`。
- 每个批次先补能复现问题的失败用例，再改实现（红 → 绿），涉及 DB / MQ / HTTP 的部分沿用依赖注入 + mock。
- 不引入新依赖，不做与问题无关的重构。

### 批次 A：任务创建流程统一（P0-1）

- 分支：`fix/webhook-task-creation`
- 改动：
  1. 在 `services/taskService.ts` 新增 `submitReviewTask(input, deps)`，封装「创建任务 → 创建 agents → 关联代码版本 → 写入 `task_queued` 事件 → 入队；入队失败则标记失败并写 error 事件」的完整流程；`createTask` 的参数同时改为选项对象（顺带完成 P2-2 的前半部分）。
  2. `POST /api/tasks` 与 Webhook 都改为调用 `submitReviewTask`；入队失败的 HTTP 映射（502）仍留在路由层。
  3. 删除 `webhook.ts` 中的 `defaultCreateReviewTask` 和「未注入发布器只打 warn」的分支：发布器改为必填依赖，未注入时启动即报错。
- 测试：
  - `submitReviewTask` 单测：验证调用顺序、入队失败时的状态与事件。
  - Webhook 单测：断言会创建 agents、写入 `task_queued`。
  - 现有 `tasks.validation.test.ts` 保持通过。
- 验收：Webhook 任务与手动任务在 DB 中的 agents、事件序列完全一致。

### 批次 B：Webhook 可靠性（P0-3、P1-3）

- 分支：`fix/webhook-reliability`
- 改动：
  1. **先应答，后处理**：签名、事件类型、payload 校验通过后立即返回 `202`，文件拉取与建任务放到后台执行（`setImmediate` + 错误日志即可，暂不引入新队列）。
  2. **去重**：
     - 新增迁移 `003_task_source_dedupe`，在 `tasks` 上为 `(source->>'repo', source->>'prNumber', source->>'headSha')` 建表达式唯一索引（只覆盖 `source IS NOT NULL` 的行）。
     - 建任务时冲突即视为重复投递，直接忽略。
     - 同时记录 `X-GitHub-Delivery` 到日志，便于排查。
  3. **代码收集**：
     - 超出总量上限时 `continue` 而不是 `break`。
     - 新增单文件上限（默认取总上限的 1/4，配置项 `GITHUB_MAX_FILE_CHARS`，同步到 `.env.example`）。
     - 把被跳过的文件列表写进任务标题或首个事件，让使用者知道审查范围。
  4. **语言推断**：按扩展名映射出各文件语言；只有一种语言时用该语言，多种语言时取变更行数最多的语言，并在代码块的 `// FILE:` 头部标注每个文件的语言。
  5. `express.raw` 的 `limit` 改为读取 `config.http.maxBodySize`。
- 测试：
  - 重复投递只建一个任务。
  - 大文件被跳过、后续小文件仍被收集。
  - 单文件上限生效。
  - 语言推断的各种组合。
  - 先应答：拉取文件的 mock 挂起时，路由仍立即返回 202。
- 验收：PR 同一 headSha 重投 3 次只产生 1 个任务、1 条评论。

### 批次 C：报告后处理收口（P0-2、P0-4、P1-2）

- 分支：`fix/report-postprocess`
- 改动：
  1. 新增 `agent/report-postprocess.ts`，导出纯函数 `finalizeReport(report, reviewConfig)`，统一负责：
     - 对 `issues` 与 **每个 `agentResults[*].issues`** 做 `redactSecrets`；
     - 对两者都按 `severityThreshold` 过滤（`maxIssues` 只截断顶层清单，维度内保留过滤后的完整结果，避免截断后维度视图与顶层不一致时用户困惑——此取舍需在 PR 中确认）；
     - 按过滤后的结果重新计算维度评分与总分（评分公式复用现有逻辑，不另起一套）。
  2. orchestrator 末尾只调用 `finalizeReport`；`consumer.ts` 的平均分改为直接使用 `report.score`，不再自行用 `agentResults` 重算。
  3. 语义缓存：存储的已是脱敏后的报告；缓存命中路径同样走 `finalizeReport`，防止历史缓存里留有未脱敏数据。
  4. **PR 评论改到终态之后**：
     - 正常路径：`completeTask` 成功后再评论，失败或取消一律不评论。
     - 缓存路径：`updateTaskStatus('completed')` 之后再评论。
     - 评论不计入 `durationMs`。
- 测试：
  - `finalizeReport` 单测：维度内的密钥被脱敏；阈值过滤同时作用于两层；评分随过滤变化。
  - Markdown 导出快照：「各维度发现」中不含密钥。
  - consumer 单测：`completeTask` 返回 false 时不调用评论函数。
- 验收：构造含 `AKIA...`、`ghp_...` 的代码样本，Markdown 导出与评论内容中均不出现原文。

### 批次 D：配置单一真源（P0-5、P1-5）

- 分支：`refactor/config-single-source`
- 改动：
  1. `config.ts` 补齐 embedding、rerank、Langfuse、`ROLE_MODELS`、`MCP_CLIENT_SERVERS`、`RAG_MODE`、`EVAL_JUDGE_MODEL` 的 schema 与默认值（默认值与当前代码保持一致，确保行为不变），并同步 `.env.example`。
  2. `llm-client.ts`：
     - `loadConfig()` / `loadMaxRetries()` 改为读取 `getConfig().llm`；
     - 并发信号量改为在首次使用时按 `getConfig().llm.maxConcurrency` 惰性创建，避免模块加载时读环境变量。
  3. `providers.ts`、`tracing.ts`、`role-router.ts`、`mcp/client.ts`、`rag/index.ts` 改为读取 `getConfig()`。
  4. `logger.ts` 的 `envDefaults()` 改为复用 `config.ts` 导出的默认值计算函数，消除重复逻辑；保留「logger 先于 config 可用」的引导顺序。
  5. 在 ESLint 中对 `server/src/**`（排除 `config.ts`、测试文件、`eval/`）启用 `no-restricted-properties` 禁止 `process.env`，防止回退。
- 风险：`LLM_PROVIDER=anthropic` 且未填 `LLM_BASE_URL` 的部署，默认地址会从 DeepSeek 变成 Anthropic。这属于修复，但仍要在 CHANGELOG 中写入「行为变更」。
- 测试：
  - `llm-client.test.ts` 改为通过 config 注入。
  - 新增用例覆盖 provider 默认地址与非法并发值。
- 验收：`server/src` 中除允许列表外 `process.env` 引用为 0。

### 批次 E：预算治理真正生效（P1-1）

- 分支：`fix/token-budget-enforcement`
- 改动：
  1. `react-loop` 增加可选的 `budget` 参数：每轮迭代发起 LLM 调用前检查，超限则停止工具循环，直接进入结构化输出阶段（只用已有分析结果）。若连结构化输出也无法执行，再降级为 `runRuleOnlyReview`。
  2. 预算按「剩余额度」在并行 reviewer 间共享（共用同一个 `TaskBudget`，用量来自 tracing 的任务级计数器，天然是累计值），不做静态切分。
  3. 报告 `governance` 增加 `budgetExceededAt`（触发时所在的 reviewer 与轮次），便于观察。
- 测试：
  - 用 mock LLM 返回固定 token 用量，验证第 N 轮后停止；
  - 并行 reviewer 中只有超限之后的调用被拦截；
  - `TASK_TOKEN_BUDGET=0` 时行为不变。
- 验收：设定较小预算时，任务总 token 不超过「预算 + 单次调用上限」。

### 批次 F：类型与结构整理（P1-4、P2-1 至 P2-6、P3）

- 分支：`refactor/shared-types-and-routes`（P1-4、P2-1 至 P2-5），`fix/api-key-compare`（P2-6），`docs/plan-ledger-sync`（P3）
- 改动：
  1. **共享类型**：
     - `client/src/types/index.ts` 中与 shared 重复的类型改为 `export type { ... } from '../../../shared/types'`，并配置 `client/tsconfig` 与 Vite 的路径（如需要再加 `@shared` 别名）；
     - 前端独有的类型（`ChatMessage`、`TaskItem` 等）保留；
     - 统一 `InjectionFinding` 命名；

## 四、执行顺序与依赖

```text
A（任务创建统一） ──► B（Webhook 可靠性）
C（报告后处理）            （与 A/B 无依赖，可并行）
D（配置单一真源）          （与 A/B/C 无依赖，可并行）
```

建议节奏：A、C、D 可同时开工；B 在 A 合入后开始；E 在 D 合入后开始；F 最后统一收尾，然后从 `develop` 合入 `master` 并打 `v1.2.0`。

## 六、不在本方案范围
